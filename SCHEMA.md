# Run file schema

Every file under `runs/`, `quarantine/` and `controls/` is one `BenchRunResult` JSON object, produced by [`@localmode/bench`](https://github.com/LocalMode-AI/LocalMode/tree/main/packages/bench) (current: schema version 3, protocol `localmode-bench/5`; files record the protocol they were measured under, and archived runs are never re-scored). The TypeScript source of truth is [`packages/bench/src/types.ts`](https://github.com/LocalMode-AI/LocalMode/blob/main/packages/bench/src/types.ts); the executable validator is `validateRunShape()` / `validateSubmission()` in the same package.

## Top level

| Field | Type | Meaning |
| --- | --- | --- |
| `protocol` | `"localmode-bench/5"` (older files: `"localmode-bench/1"` to `"localmode-bench/4"`; the leaderboard shows v5 and v4 rows side by side, never mixed) | Versioned protocol identifier |
| `schemaVersion` | `3` (older files: `1` and `2` were rewritten to 3 by the scrub on 2026-09-21; see Schema versions) | Result JSON schema version |
| `runId` | string | UUID of the run (also the filename) |
| `createdAt` | ISO 8601 string | UTC timestamp |
| `harness` | `{ name, version, appVersion?, runtimeVersions?, commit?, series?, coldStart?, control? }` | Harness identity. Since bench 0.3.0 `runtimeVersions` maps each runtime package the host bundled to its version (e.g. `"@huggingface/transformers": "4.2.0"`, `"@wllama/wllama": "3.5.1"` - the CDN pin that executes) and `commit` is the host build's git commit when exposed. Since bench 0.9.0: `series` (`{ id, index, count }`) marks a run of a consecutive series on one device with the same settings, one fresh page load per run (`id` shared by the series, 1 to 64 characters; `index` 1-based and at most `count`; `count` 1 to 1000); `coldStart: "provider-caches-cleared"` marks a run that started right after the page deleted its providers' model caches (Cache API, IndexedDB, OPFS) and found them empty. `coldStart` never claims a fresh browser profile: the browser's HTTP disk cache and Gemini Nano are out of a page's reach, so read each cell's `load.cached` together with it. Both are absent on runs outside a series or not started cold. Since bench 0.9.1 `series` may also carry `cooldownMs` (the idle wait configured between the runs of the series, integer ms from 0 to 3,600,000; recorded on every run of the series, run 1 included, because it describes the series) and `idleBeforeMs` (the idle time measured before this run started, from the moment the previous run of the series was kept to this run's start across the page reload, integer ms from 0 to 2,592,000,000; absent on run 1 and on a run resumed by hand after a pause). The cool-down is idle time on the page between runs, not a protocol setting: a 7-run back-to-back Quick series on a 15 W class laptop showed the llama.cpp CPU decode falling from about 135 to about 85 chars/s from run 3 on, so laptop and phone series need a recorded pause. Runs from 0.9.0 series carry neither field. Since bench 0.9.6 `control` marks a control run (see Control runs below; kind `fixed-order` since bench 0.9.7, kind `wasm-default` with its `wasmLane` since bench 0.9.8, kinds `wasm-q8` and `wasm-threads` with theirs since bench 0.9.9, kind `wllama-compat` with its `wllamaBuild` since bench 0.9.13); absent on every protocol run |
| `suite` | `quick \| standard \| thorough \| custom` | Suite preset |
| `environment` | object | Full environment capture (see below) |
| `fingerprint` | object | Deterministic matmul calibration microbenchmark (`mflops`, `iterations`, `durationMs`, `checksum`) |
| `cells` | array | One entry per (runtime × model × workload) cell (see below) |
| `events` | array | Suite-level trace events (`suite-start`, `visibility-hidden`, `wakelock-released`, `pressure-change`, `cell-timeout`, `cell-retry`, `iteration-redo`, …) with timestamps. `pressure-change` is recorded per one-second sample in files produced before bench 0.4.0 and on state transitions only afterwards |
| `clientSummaries` | array? | Client-computed summaries (advisory; the server recomputes from traces) |
| `nonce` | absent | The submission carried a server-issued session nonce; the server strips it before publishing (since schema 3; older files may still carry one) |
| `digest` | string | SHA-256 hex of the canonical JSON of this object without `digest` and `nonce` (files published before schema 3 were digested with the nonce included; `verifyRunDigest` in `@localmode/bench` accepts both) |
| `scrubbedAt` | string? | ISO time at which the file was rewritten by the publication scrub (fields removed under schema 3, digest recomputed); absent when the file is exactly what the client submitted |

## `environment`

Browser identity with provenance (`ua-ch` on Chromium; `ua-parse` elsewhere with `os.version: "unknown-frozen"` - UA strings are frozen by design; since bench 0.7.1 this includes iOS, where WebKit froze the token at `18_7`: a Safari or Firefox iOS run recorded earlier with `os.version: "18.7"` and a Safari version of 26 or higher is a frozen reading, and `browser.version` carries the OS generation), WebGPU adapter info (`vendor`, `architecture`, limits, features), hardware fields **labeled clamped** (`cores`, `deviceMemoryGB` - browsers cap or randomize them), cross-origin isolation, WASM SIMD, storage estimate, battery charging state, compute-pressure availability, inferred `timerResolutionUs`, and an optional `userReportedDevice` free-text field (displayed as user-reported, never trusted; paid-study runs carry `prolific:<12-hex SHA-256 prefix>` here, never a participant id). Since bench 0.9.4 a paid-study run may also carry `userReportedHardware` (`{ gpu?, chassis?, ramGB?, otherAppsRunning? }`): the hardware the participant reported on the page before the run, because the browser masks the GPU name, caps the RAM it discloses and never says whether the device is a laptop. `gpu` is the graphics card or chip as typed (1 to 64 characters after trimming, no control characters, whitespace collapsed by the server), `chassis` is `laptop`, `desktop` or `other`, `ramGB` is the chosen RAM bucket in GB (4 to 128, where 128 means "128 GB or more"; `null` for "Not sure"), and `otherAppsRunning` says whether games, video calls or editing software were running. The answers are self-reported, never checked against the device, and absent on every run outside a paid study; read them beside the browser-disclosed fields (`gpu.vendor`, `gpu.architecture`, `gpuModel`, `hardware.deviceMemoryGB`), never in place of them. The digest covers the field like the rest of `environment`. Additive: the schema version and the protocol are unchanged.

Since `@localmode/bench` 0.3.0 (additive optional fields; the schema version is unchanged and older files simply lack them) a run also records everything else the browser discloses, every probe guarded so a missing API records nothing for its key:

| Field | Meaning |
| --- | --- |
| `userAgent` | Raw `navigator.userAgent`, kept verbatim so future parsers can re-derive fields |
| `browser.engine` / `vendor` / `webdriver` / `pdfViewerEnabled` | Rendering engine (`Blink` / `Gecko` / `WebKit`), `navigator.vendor`, automation flag, PDF viewer (a headless signal) |
| `os.bitness` / `wow64` / `navigatorPlatform` | UA-CH bitness and WoW64 flag (Chromium); legacy `navigator.platform` |
| `device` | `{ type: phone \| tablet \| desktop \| xr \| tv \| unknown, mobile, formFactors?, maxTouchPoints, pointerCoarse?, hoverNone?, displayMode? }` - form factor from UA-CH form factors, the UA, and touch points (an iPad reporting as a Mac is unmasked by `maxTouchPoints`) |
| `hardware.jsHeapSizeLimitBytes` / `jsHeapUsedBytes` | `performance.memory` ceiling and idle usage (Chromium) |
| `gpu.subgroupMinSize` / `subgroupMaxSize` / `preferredCanvasFormat` / `wgslLanguageFeatures` | Further WebGPU adapter identity; `limits` now carries 12 limits |
| `webgl` | `{ contextKind, vendor, renderer, version, shadingLanguageVersion, maxTextureSize, maxRenderbufferSize, maxVertexUniformVectors, maxFragmentUniformVectors, extensionCount, softwareRenderer }` (unmasked strings where `WEBGL_debug_renderer_info` exists) |
| `gpuModel` | GPU model: the WebGPU adapter description where a browser fills it in, else parsed from the WebGL renderer string with the ANGLE wrapper, PCI id and Direct3D suffix removed (`"Apple M4"`, `"NVIDIA GeForce RTX 4070"`, `"Mali-G78 MP20"`; Firefox coarsens it to e.g. `"Apple M1, or similar"`; Playwright/headless software GL reports SwiftShader) |
| `flags.secureContext` / `flags.wasm` | Secure context; the WebAssembly proposal matrix probed by validating canonical modules (the wasm-feature-detect 1.9.0 detection modules): `simd, relaxedSimd, threads, bulkMemory, exceptions, exceptionsFinal, extendedConst, gc, memory64, multiMemory, multiValue, mutableGlobals, referenceTypes, saturatedFloatToInt, signExtensions, tailCall, typedFunctionReferences, wideArithmetic, jspi, typeReflection, streamingCompilation, jsStringBuiltins`, plus `maxMemoryPages` (largest 32-bit `WebAssembly.Memory` maximum the engine accepts; 65536 = 4 GiB) |
| `apis` | Presence checks: `webgpu, webgl2, webnn, opfs` (getDirectory resolved), `persistedStorage, indexedDB, cacheApi, serviceWorker, webWorkers, offscreenCanvas, webLocks, broadcastChannel, wakeLock, computePressure, performanceMemory, measureUserAgentSpecificMemory, schedulerYield, webCodecs, audioWorklet, mediaDevices, webTransport`, and the Chrome Built-in AI `availability()` verdicts `promptApi, summarizerApi, translatorApi` (en→es), `languageDetectorApi` where those globals exist |
| `storage.usageDetails` | Per-storage-system usage where the browser breaks it down |
| `power` | `{ batterySupported, charging?, level? }`; `level` is rounded to the quarter since schema 3 (the exact percentage and the Battery API times were removed: they track a device) |
| `network` | `{ supported, effectiveType?, type?, downlinkMbps?, rttMs?, saveData?, online? }` from the Network Information API (Chromium; `online` everywhere) |
| `display` | `{ width, height, availWidth, availHeight, dpr, colorDepth, orientation, viewportWidth, viewportHeight, hdr, wideGamut, isExtended }` (superset of `screen`; the two display preferences were removed in schema 3) |
| `locale` | `{ locale }`, the BCP 47 tag only, since schema 3 (the time zone, UTC offset, and calendar place a device in a city and are not captured; `languages` was removed for the same reason) |
| `pageOrigin` / `visibilityState` | Origin the run executed on (production vs local) and tab visibility at capture |

Note: `hardware.coresClamped` in files produced before bench 0.3.0 is `true` for every Chromium run (the label compared the UA-CH brand name "Google Chrome" against "Chrome"); Chromium reports real logical cores, so treat those values as unclamped when `browser.source` is `ua-ch`.

## `cells[]`

| Field | Meaning |
| --- | --- |
| `cellId` | `runtimeId/benchModelId/workloadId` |
| `runtimeId` | `transformers-webgpu \| transformers-wasm \| webllm \| wllama \| wllama-webgpu \| litert \| chrome-ai \| mediapipe`. Since `localmode-bench/3`, `wllama` is llama.cpp on the CPU (`n_gpu_layers: 0`) and `wllama-webgpu` offloads every layer to WebGPU; in v1/v2 files the single `wllama` lane ran on WebGPU wherever `environment.gpu.available` is true while recording `resolvedBackend: "wasm"` (wllama 3.5's default offload, unnoticed by the harness) |
| `runtimeVersion` | Version of the runtime package that produced the cell (since bench 0.3.0; Chrome Built-in AI has none - the browser version is its identity) |
| `model` | Static model reference (provider model id, quantization, declared size, URL). `model.quantization` is the bench catalog's label for the pairing, not a recorded fact about the model the run loaded. For the Transformers.js embedding pairing (`bge-small-en`, `Xenova/bge-small-en-v1.5`) the label reads `q8`, but a protocol run loads the fp32 model on both lanes (`transformers-wasm` and `transformers-webgpu`) in every release so far: fp32 is the provider's default, and the harness never passes the label to it. On the WASM lane of a protocol run the preload fetches the q8 files (Transformers.js's WASM default) while the timed model uses the fp32 file, also in every release so far, so that pairing's cold-start `load` segment measures the preload, and the fp32 download falls in the first warmup (`warmupMs`); on the WebGPU lane the preload and the timed model both use the fp32 file. Changing the preload would be a protocol change, so it is unchanged. What bench 0.9.8 changed is the record: no earlier cell records the loaded dtype, and `runtimeConfig.dtype` names it: since bench 0.9.8 (site build 2.16.14) the `transformers-wasm` cells record it for both the language and the embedding model (`fp32` for the embedding model on a protocol run and on a `wasm-threads` control run, `q8` on a `wasm-default` or `wasm-q8` control run), and the `transformers-webgpu` language-model cells record it as before (the catalog label, which the provider's `q4` default matches); the `transformers-webgpu` embedding cells record no `dtype` `model.url`, where the catalog declares one (the LiteRT and llama.cpp lanes), is a branch URL (`/resolve/main/`) before site build 2.16.16 and a URL pinned to a repository revision (`/resolve/<40-hex commit>/`) since: a branch URL names whatever file the repository held when that browser first downloaded it, and the `Qwen3-0.6B.litertlm` behind the LiteRT Qwen3 URL was replaced on 2026-10-12 (see the erratum in the [README](./README.md)) |
| `workloadId` / `workloadKind` | e.g. `chat-pp128-tg128` / `llm-generate` |
| `resolvedBackend` | Backend actually used (probed, never the requested one). For the wllama lanes since v3 it follows llama.cpp's own `offloaded N/M layers to GPU` load report when one was printed. Before bench 0.9.9 a `wllama-webgpu` cell whose report read `unreported` recorded the lane's requested `webgpu`: on a timed cell that is the CPU fallback (llama.cpp prints no offload line when it finds no GPU device, so the lane ran on the CPU; read such a cell as a CPU run), and on a `warm-reload` cell it is the prediction (see `localmode-bench/4` below). Since bench 0.9.9 (site build 2.16.15) the llama.cpp lanes record `webgpu` only when at least one layer was offloaded, `wasm` otherwise (CPU fallback included), and `unknown` when the record was read before the engine loaded; the validator rejects a cell whose backend disagrees with its `offloadedLayers` count or its `gpu_fallback` For the LiteRT lane before bench 0.9.10 (site build 2.16.16) it came from a WebGPU probe (`gpu` whenever the browser had a WebGPU adapter), not from the engine: LiteRT-LM 0.12.1's GPU backend refuses to stream-load the Qwen3 0.6B file and the provider then runs it on the CPU backend, so read those LiteRT Qwen3 `gpu` cells as most likely CPU runs. Since 0.9.10 it is the backend the engine loaded on (`gpu` or `cpu`; `unknown` before the engine loaded), and the validator rejects a LiteRT cell whose backend disagrees with its `requestedBackend`/`gpu_fallback` |
| `runtimeConfig` | Since bench 0.5.0: the adapter's post-load configuration record, per cell (wllama: `n_threads` requested, `n_gpu_layers` requested, `webgpu_adapter`, `offloadedLayers` "N/M", `cache_prompt`, since v4 `mmproj: false` on language lanes, and, on runs whose `harness.runtimeVersions["@localmode/wllama"]` is 3.4.2 or later, `multithread` and `n_threads_used`, the pool wllama actually built from its own `isMultithread()` / `getNumThreads()`, so a lane that fell back to one thread says so; since bench 0.9.9 (site build 2.16.15), on the WebGPU lane (`n_gpu_layers` not 0) once the engine loaded, `gpu_fallback`: `true` when llama.cpp offloaded no layer (`offloadedLayers` `0/M` or `unreported`), so the lane ran on the CPU and `resolvedBackend` is `wasm`, `false` when it offloaded at least one; absent on the CPU lane and on every earlier run; Transformers.js: `device`, `dtype`, `worker`; on runs from localmode.ai site build 2.16.14 on (`harness.runtimeVersions["@localmode/bench"]` 0.9.8 or later), the `transformers-wasm` cells also carry `numThreads`, the WASM thread count ONNX Runtime initialised with in the lane's worker, read back from the runtime env after its first session (ONNX Runtime's own default, `min(4, ceil(cores / 2))` on a cross-origin-isolated page, on a protocol run), and the lane's embedding cells carry `dtype: "fp32"`, the dtype the provider loads an embedding model at; earlier runs carry neither); since bench 0.9.13 (site build 2.16.19) every llama.cpp cell (`wllama`, `wllama-webgpu`), on protocol and control runs alike, also carries `wllamaBuild`: the wllama WASM build its worker started on, `memory64` (wllama's default build, 64-bit memory with JSPI where the browser has it) or `compat` (its compatibility build, `@wllama/wllama-compat`: 32-bit memory, no JSPI), as the provider recorded it. wllama 3.5.1 starts the compatibility build by itself only on a browser without JSPI or Memory64, such as Safari, and never on Firefox, so protocol runs record `memory64` in Chrome and Firefox; the field is present once wllama has started its worker and absent on earlier runs. The validator rejects any other value and the field on a cell that is not llama.cpp; LiteRT, since bench 0.9.10 (site build 2.16.16; earlier LiteRT cells carry no `runtimeConfig`): `modelRevision` (the 40-hex commit the model URL is pinned to, or `unpinned`), `webgpu_adapter`, and once the engine loaded `modelBytes` (the bytes the engine read: the download on a network load, the cached file otherwise), `requestedBackend` (`gpu` or `cpu`, the first load attempt) and, when that was `gpu`, `gpu_fallback` (`true` when the engine ended on the CPU backend). Additive; the schema stays 3 and the protocol `localmode-bench/5` |
| `load` | Download/cache phase: `cached` (cold=false / warm=true), start/end timestamps, progress milestones |
| `warmupMs` | Untimed first-inference readiness (engine init + shader/JIT compile). Cold start = load + warmup |
| `iterations` | LLM: `{ startT, chunks: [{t, c}], endT, text, providerUsage?, finishReason, gates }` - per-chunk wall-clock trace + full generated text. Embedding: `{ startT, endT, count, dimensions, gates }`. The LLM `text` is also the evidence for the date partition of the Llama 3.2 1B cells: its chat template writes the device's local date into the prompt, and on `transformers-webgpu` every iteration of one date gives the same `text` (see Known prompt limitation in the [README](./README.md)) |
| `memory` | Bytes at protocol points (`baseline`/`postLoad`/`postRun`, and since v2 `atError` for cells that failed) + which API measured them |
| `quality` | Optional fidelity-lane score (tinyMMLU accuracy or STS-B Spearman). Since v2, MMLU cells also carry raw per-item `outputs` (capped at 400 chars each) and a `parseRate` (fraction of parseable answers; a low value marks a format-limited score), so scores are recomputable |
| `status` / `invalidReasons` | `ok \| invalid \| error \| skipped`. Since v2 a timed LLM iteration generating fewer than 16 chars is gated `degenerate-output` and the cell is `invalid`. The gate checks length only, not coherence: the Adreno 830 `wllama-webgpu` SmolLM2 chat cells are `ok` although their `text` is incoherent (see Known limitations in [NOTES.md](./NOTES.md#known-limitations)). `skipped` cells carry the reason in `invalidReasons` (`runtime unavailable: ...`, `lane disabled by the submitter`); since bench 0.4.0 every cell a suite defines is present, so a suite label describes what was attempted and a skipped cell says why it was not |
| `discardedIterations` | Since bench 0.5.0: timed iterations the tab was hidden during, kept with their gates (`started-hidden`, `hidden-during-run`) and never scored; the runner waited for the tab and repeated each of them (`iteration-redo` trace event) |
| `attempts` | Since bench 0.5.0: failed attempts that preceded the recorded outcome, oldest first (`{ error, at }`); the runner retries a cell up to twice after a watchdog timeout or a provider error and never silently |
| `error` | `{ name, message, cause?, causeName?, causeStack? }` for `error` cells; since v2 `cause` carries the wrapped provider error's message, and since bench 0.4.0 `causeName` its name and `causeStack` its stack (capped at 4,000 characters; a WASM abort such as wllama's `RuntimeError` "(ABORT) " names its native frame only there) |
| `status` | `ok \| invalid \| error \| skipped` - invalid cells carry `invalidReasons`, never silent retries |

## Metric definitions (how to recompute)

- **TTFT** = first chunk with `c > 0` → `t − startT`.
- **Decode chars/s** = `(Σ chunk chars − first chunk chars) / (t_last − t_first) × 1000` - endpoints-based, first token excluded (MLPerf Client TPS definition).
- **Tokens/s** - apply the model's tokenizer to `text` post-hoc; provider-reported `providerUsage` is auxiliary only (its `fidelity` field says why: `estimated` or `chunk-count`).

`index/summary.json` is an array of light per-run summaries (`RunIndexEntry` in [`apps/ui/src/lib/bench/store.ts`](https://github.com/LocalMode-AI/LocalMode/blob/main/apps/ui/src/lib/bench/store.ts)) used to render the leaderboard without fetching every run file. Each entry carries two device groupings: `deviceClass`, the coarse class every browser can supply (platform + WebGPU adapter vendor-architecture, e.g. `macos/apple-metal-3`, `windows/amd-rdna-2`, `linux/no-webgpu`), and, since bench 0.7.1, `deviceSubclass`, the class split by the GPU model where the browser names a specific part (`macos/apple-m1-pro`, `android/adreno-650`; `refineDeviceClass()` in `@localmode/bench`). Where the browser names nothing more specific (WebKit's `Apple GPU`, Windows' generation-less `AMD Radeon(TM) Graphics`, Firefox's masked `..., or similar` buckets) or the device has no WebGPU, the subclass equals the class. Every entry carries the fields the current submit path writes, including `deviceSubclass` for runs recorded before 0.7.1: the index is rebuilt from the run files with the submit path's own entry builder (see the README), and the run files themselves are unchanged. For an index entry without `deviceSubclass` the leaderboard derives it from `deviceClass` and `gpuModel` with the same function. Leaderboard rows group by subclass; the coarse class remains the unit for cross-device rollups. Since bench 0.9.5 the architecture in `deviceClass` and `deviceSubclass` corrects the browser's label for the AMD integrated GPUs listed in `AMD_DEVICE_ID_ARCHITECTURE` in `@localmode/bench`, read from the PCI device id in the run's `environment.webglRenderer`: Chromium takes the label from Dawn's `gpu_info.json`, which matches AMD ids under a 0xFFF0 mask and so reports Barcelo (0x15E7) and Lucienne (0x164C), which are Vega / GCN 5, as `rdna-2`, and Kaveri (0x1304 to 0x131D, GCN 2) as `gcn-1`. Such an entry's `gpuArchitecture` holds the corrected architecture and `gpuArchitectureReported` the browser's label; `gpuArchitectureReported` is present only when the two differ. The run file keeps the browser's label in `environment.gpu.architecture`. Entries for runs recorded since bench 0.3.0 also carry the run's disclosed device identity (`engine`, `osVersion`, `architecture`, `gpuArchitecture`, `gpuModel`, `deviceType`, `deviceModel`, `cores`, `deviceMemoryGB`, `jsHeapSizeLimitBytes`, `storageQuotaBytes`, `crossOriginIsolated`, `webgpu`, `timerResolutionUs`, `webdriver`), `harnessVersion`, `runtimeVersions`, `userReportedDevice`, and each cell's `runtimeVersion`, so cohort analyses can run on the index alone. Entries of runs that carry `userReportedHardware` (since bench 0.9.4) also carry `reportedGpu`, `reportedChassis` and `reportedRamGB`; the keys are absent when the run has no answer, and `reportedRamGB` is absent for "Not sure", so every earlier entry is unchanged. An entry may also carry `importedAt` (ISO 8601 time): the run's upload never went through, and a maintainer added it from the file the participant exported, with `scripts/import-exported-run.ts` in `apps/ui`. Such a run passed the same pipeline as a submission (digest verification, `validateSubmission` with the quarantine decision, the publication scrub, the same path and file bytes the submit route writes) except the live session-nonce check, which an exported file can no longer pass; its run file is unchanged by the import. The key is absent on every submitted run, and an index rebuild keeps it. An imported entry may also carry `importNote`, which says what the import changed in the run besides the nonce. Its one value, `"stale series record removed"`, marks a run the page assembled after a series had finished, so its `harness.series` was numbered past its count (`index` greater than `count`) and the shape check refused it; the import (with `--drop-stale-series`) verified the participant's digest, removed `harness.series` as a publication scrub, stamped `scrubbedAt` and recomputed the digest. The run is a standalone run, not part of that series. The key is absent on every other entry, and an index rebuild keeps it.

## Errata (`index/errata.json`)

`index/errata.json` is a JSON array of erratum entries (`ErratumEntry` in [`@localmode/bench`](https://github.com/LocalMode-AI/LocalMode/tree/main/packages/bench)), written by a maintainer, never by the submission API:

| Field | Type | Meaning |
| --- | --- | --- |
| `runId` | string | The run the cells belong to; a run file under `runs/` or `quarantine/` |
| `cellIds` | string[] (non-empty) | Cell ids (`runtimeId/benchModelId/workloadId`) of that run, each recorded `ok` and listed once |
| `reason` | string | Why the cells are excluded, for a reader of the dataset |
| `recordedAt` | string | When the erratum was recorded: an ISO 8601 date (`2026-10-22`) or date-time |
| `reference` | string | Where the evidence is documented (a section of this README, an issue, a commit) |

No other field is allowed (in particular no replacement value: an erratum is an exclusion, never a re-score). Listed cells enter no aggregate: the leaderboard rows (`aggregateIndex` in the app, `aggregateRuns` in the package) leave them out of every median and count them in `excludedByErratum`, per row and, in the leaderboard API response and the analysis CLI output, in total (`{ cells, runs }`). A row whose every cell is listed stays with `submissions` 0. The run files and `index/summary.json` are unchanged: a listed cell keeps its index entry, status and values. An entry names only cells recorded `ok`, because a cell with any other status (`invalid`, `error`, `skipped`) already enters no aggregate; `validateErrata` in `@localmode/bench` refuses such a cell, a run this dataset does not hold, a cell the run does not have, a cell listed twice and any malformed entry, and the leaderboard, the analysis CLI and the index rebuild tool refuse an errata file that fails it. An erratum changes no measurement rule, so it does not change the protocol version. The file is absent or `[]` when nothing is excluded.

## Analysis exports

`scripts/analyze.ts` in [`packages/bench`](https://github.com/LocalMode-AI/LocalMode/tree/main/packages/bench) turns a clone of this dataset into `leaderboard.csv`, `iterations.csv`, `cells.csv` and `runs.csv` (columns documented in the package's [NOTES.md](https://github.com/LocalMode-AI/LocalMode/blob/main/packages/bench/NOTES.md#csv-columns)). Since bench 0.9.11 it applies `index/errata.json` to `leaderboard.csv` only, which gains a last column `excludedByErratum`, and writes `errata.txt` (the file applied, the tally and each excluded cell with its reason); `iterations.csv`, `cells.csv` and `runs.csv` keep every cell. Since bench 0.9.0 `runs.csv` carries `seriesId`, `seriesIndex`, `seriesCount` and `coldStart` from `harness.series` and `harness.coldStart`, after `validationFlags` and before the `rv_*` runtime-version columns; they are empty on runs that do not carry the fields. Since bench 0.9.1 seven more columns follow `coldStart`, still before the `rv_*` columns: `seriesCooldownMs` and `seriesIdleBeforeMs` (`harness.series.cooldownMs` and `harness.series.idleBeforeMs`, empty when not recorded), `pressureSamples` (the number of `pressure-change` events in the run's `events`, one per Compute Pressure state transition; 0 when the browser has no Compute Pressure API), and `pressureCriticalFraction`, `pressureSeriousFraction`, `pressureFairFraction`, `pressureNominalFraction`: the fraction of the suite wall time (`suite-end` minus `suite-start`) spent in each state, computed from the event timestamps, rounded to four decimals, empty when the run has no sample. The state at `suite-start` is the last transition at or before it, and time before the first known state counts toward none, so the four fractions sum to less than 1 when the first sample arrived mid-suite. The columns describe the runs; no leaderboard or validation rule reads them. Since bench 0.9.3 `runs.csv` ends, after the `rv_*` columns, with `powerCharging` and `powerLevel` (`environment.power.charging` and the quarter-rounded `environment.power.level`; both empty when the browser has no Battery API), and `cells.csv` ends, after `errorCause`, with `cellStartedAt` and `cellEndedAt`: ISO 8601 UTC times, rounded to the millisecond, of the earliest and latest page-relative timestamp the cell records (`load.startT` and `load.endT`, the load progress samples, `load.endT` plus `warmupMs`, the `startT` and `endT` of every kept and discarded iteration, the `at` of every failed attempt), mapped to wall time as `createdAt - (suiteEnd - t)` with `suiteEnd` the `t` of the run's last `suite-end` event, which the runner records just before it stamps `createdAt`. Both are empty on a skipped cell, on a cell that records no timestamp (a quality cell over a model an earlier cell loaded: the quality lanes record no timing), and on a run without `suite-end`. Every earlier column keeps its name, position and value. Since bench 0.9.4 `runs.csv` ends, after `powerLevel`, with `reportedGpu`, `reportedChassis`, `reportedRamGB` and `reportedOtherApps` from `environment.userReportedHardware`: empty when the run carries no answer, and `reportedRamGB` empty for "Not sure". Every earlier column keeps its name, position and value. Since bench 0.9.6 `runs.csv` ends, after `reportedOtherApps`, with `controlKind` and `controlRuntimeOrder`: `harness.control.kind` (`order-reversed`, since bench 0.9.7 `fixed-order`, since bench 0.9.8 `wasm-default`, since bench 0.9.9 `wasm-q8` and `wasm-threads`, since bench 0.9.13 `wllama-compat`) and the runtime order the control run used, joined by `>`; both empty on a protocol run. The analysis CLI reads control runs like any run file, and `leaderboard.csv` never includes one.

## Control runs (`controls/`)

Since bench 0.9.6 a run may carry `harness.control` (`{ kind, runtimeOrder }`), which marks a control run: a control experiment for the methodology. The protocol executes its cells in a fixed runtime order (`RUNTIME_EXECUTION_ORDER` in `@localmode/bench`: `transformers-wasm`, `transformers-webgpu`, `chrome-ai`, `webllm`, `mediapipe`, `litert`, `wllama-webgpu`, `wllama`), a reproducibility measure that ties each lane to its position in the suite (what ran before it, how long the page has been busy). A control run executes the same suite in the runtime order its kind names, so that the lane ratios of two orders can be compared, or with one lane's configuration changed. There are nine kinds. `order-reversed` (since bench 0.9.6) reverses the protocol order. `fixed-order` (since bench 0.9.7) keeps the protocol order itself and is marked as a control run: it is the same-build, same-day reference series for an order-reversed series. The protocol runs in `runs/` may come from another browser build, and a browser update can move a lane on its own, so an order-reversed series is compared with a fixed-order series recorded on the same machine, with the same browser build, on the same day and with the same settings. `wasm-default` (since bench 0.9.8) keeps the protocol order and runs the Transformers.js WASM lane (`transformers-wasm`) at the runtime's own defaults instead of the protocol's configuration: the lane's models load at dtype `q8` (Transformers.js 4.2's default on the WASM device; a protocol run loads the language model's `q4` files, which the provider uses on both devices, and the embedding model at `fp32`), and ONNX Runtime's WASM thread count is set to the browser's `navigator.hardwareConcurrency` instead of ONNX Runtime's own default (`min(4, ceil(cores / 2))` on a cross-origin-isolated page). Every other lane and every rule is the protocol's; it is compared with a fixed-order series recorded on the same machine, browser build, day and settings. `wasm-q8` and `wasm-threads` (since bench 0.9.9) each make one of the two changes `wasm-default` makes, in the protocol order: `wasm-q8` loads the WASM lane's models at `q8` and leaves ONNX Runtime's thread count at the runtime's own default (the page does not set it), and `wasm-threads` keeps the protocol's files (the language model's `q4` files, the embedding model at `fp32`) and sets the thread count to `navigator.hardwareConcurrency`. With `fixed-order` (neither change) and `wasm-default` (both) the four kinds form a 2x2 factorial over the dtype and the thread count, recorded on the same machine, browser build, day and settings, on the Standard tier (the smallest suite with a Transformers.js WASM language-model cell). `wllama-compat` (since bench 0.9.13) keeps the protocol order and every lane's protocol configuration, except that both llama.cpp lanes (`wllama-webgpu` and `wllama`, language and embedding models) load through wllama's compatibility build (`@wllama/wllama-compat`: 32-bit memory, no JSPI) instead of the memory64 build. wllama 3.5.1 picks the compatibility build by itself only on a browser without JSPI or Memory64 (Safari) and never on Firefox, so the llama.cpp lanes of every Firefox run in `runs/` ran the memory64 build; the page forces the compatibility build in every browser, so the kind is browser-independent, and it is compared with a fixed-order series recorded on the same machine, browser build, day and settings. `current-releases` (since bench 0.9.14) keeps the protocol order and every lane's protocol configuration but runs four runtimes at their npm releases current on 23 October 2026 instead of the pinned ones: Transformers.js 4.3.1 (both lanes, with the ONNX Runtime Web build it ships, 1.31.0-dev.20260914), WebLLM 0.2.86, wllama 3.8.1 (both llama.cpp lanes, with its compatibility build at the same version) and LiteRT-LM 0.18.0; MediaPipe and Chrome Built-in AI keep their versions. The page loads a second build of the provider packages, made from the same provider source against those releases, only on this kind. A lane that fails on a current release is an error cell like any other, a result of the control. `ort-profile` (since bench 0.9.14) keeps the protocol order and configuration, and after the Transformers.js Qwen3 0.6B generation cells (WebGPU and WASM) runs an untimed profiling pass per cell in a fresh session with ONNX Runtime Web's profiler on; the cell's timed iterations are unprofiled and compare with a fixed-order run's, and the pass's operator events, aggregated, are the cell's `profile`. `llamacpp-profile` (since bench 0.9.14) keeps the protocol order and configuration and time-stamps the llama.cpp lanes' token delivery path (the wllama worker's receipt and reply, the page's send and receipt, the chunk); each llama.cpp generation cell carries the per-request statistics as its `profile`. Every kind runs on any tier (`suite` records it).

| Field | Meaning |
| --- | --- |
| `harness.control.kind` | `order-reversed`, `fixed-order`, `wasm-default`, `wasm-q8`, `wasm-threads`, `wllama-compat`, `current-releases`, `ort-profile` or `llamacpp-profile` |
| `harness.control.runtimeOrder` | The runtime order the run executed, first runtime first. For `order-reversed` it is exactly the reverse of `RUNTIME_EXECUTION_ORDER` (`wllama` first, `transformers-wasm` last); for every other kind it is exactly `RUNTIME_EXECUTION_ORDER` (`transformers-wasm` first, `wllama` last). Within a runtime the catalog order is kept. The runner orders the cells by it and refuses any other order, and the validator rejects any other kind or order, so the record names the order the run used. The reversed order also runs the Transformers.js WebGPU lane before its WASM lane, which the protocol order avoids; a WebGPU session failure that takes the WASM lane with it is recorded as an error, as on any run |
| `harness.control.wasmLane` | `wasm-default`, `wasm-q8` and `wasm-threads` only, required there and refused on every other kind: the Transformers.js WASM lane settings the run applied, exactly `{ dtype: "q8", numThreads, simd: true }` on `wasm-default`, `{ dtype: "q8", numThreads: null, simd: true }` on `wasm-q8` and `{ dtype: "q4", numThreads, simd: true }` on `wasm-threads`. `dtype` `q8` means every model of the lane loaded its q8 files; `q4` means the protocol's files (the language model's `q4` files, the embedding model at `fp32`), and each cell's `runtimeConfig.dtype` records the dtype that model loaded at. `numThreads` (an integer from 1 to 1024) is the ONNX Runtime WASM thread count the page set, its `navigator.hardwareConcurrency`, or `null` when the page left it to ONNX Runtime (`wasm-q8`). Each `transformers-wasm` cell's `runtimeConfig` records the `numThreads` ONNX Runtime actually initialised with (its own default on `wasm-q8`; one thread if the page could not run WASM threads). `simd` is always `true` (ONNX Runtime Web ships SIMD builds only) |
| `harness.control.wllamaBuild` | `wllama-compat` only, required there and refused on every other kind: always `"compat"`, the wllama build both llama.cpp lanes loaded through. Each llama.cpp cell's `runtimeConfig.wllamaBuild` records the build its worker actually started on, and the validator rejects a `wllama-compat` run whose loaded llama.cpp cell records anything but `compat` |
| `harness.control.runtimeVersions` | `current-releases` only, required there and refused on every other kind: package name to the version the run loaded, for `@huggingface/transformers`, `@mlc-ai/web-llm`, `@wllama/wllama`, `@wllama/wllama-compat` and `@litert-lm/core`, and optionally `onnxruntime-web` |
| `cells[].runtimeConfig.runtimeVersion` | `current-releases` only: on every cell of the lanes the kind changes (`transformers-webgpu`, `transformers-wasm`, `webllm`, `wllama`, `wllama-webgpu`, `litert`) that carries a `runtimeConfig`, the version of the lane's package from `harness.control.runtimeVersions` (the cell's `runtimeVersion` names it too); the validator rejects any other value, and the field on any other run or lane. A LiteRT cell of the kind also records `thoughtChannel: "inline"`: on LiteRT-LM 0.18 the provider keeps text the engine streams on a message's thought channel, inline in one `<think>` block, as the pinned release delivered the same reasoning inside the content |
| `cells[].profile` (`ort-profile`) | On a Transformers.js Qwen3 generation cell: `{ kind: "ort-operators", pass: { warmupTokens, maxTokens, failedMaxTokens? }, runs, modelRunMs, nodeEvents, nodeMs, gpuMs?, operators, foldedRows?, truncated? }`. The pass ran in a fresh profiled session, in a fresh dedicated worker: a warmup request of `warmupTokens` new tokens, then one request with the cell's prompt and `maxTokens` new tokens (the cell's own budget unless a pass ran out of WASM memory; `failedMaxTokens` lists the budgets that did, each retried at half). `runs` is that request's session runs (the prefill, then one per decode step), `modelRunMs` their summed `model_run` time. Each of the at most 100 `operators` rows (largest first, the rest folded into an `(other)` row per phase and timing, counted in `foldedRows`) is `{ phase: "prefill" \| "decode", timing: "node" \| "gpu", opType, kernel, provider, totalMs, count }`: `node` is ONNX Runtime's per-node kernel time on the host thread (the computation on the CPU provider; recording and dispatch on the WebGPU provider), `gpu` the WebGPU provider's GPU timestamps per program (quantized by Chrome unless it ran with WebGPU developer features). `truncated` marks a profile that holds fewer runs than the request made. Profiled requests run slower than unprofiled ones, so a profile gives operator shares, not throughput. The raw events of each pass are not in the run file |
| `cells[].profile` (`llamacpp-profile`) | On a llama.cpp generation cell: `{ kind: "llamacpp-delivery", binEdgesMs, iterations }`, one entry per request (warmup excluded, at most 64): `tokens` (replies that carried a token), `chunks`, `messages` (every reply, empty polls included), `clockOffsetMs` (the worker clock's estimated offset from the page's, the median of `((wrecv - send) + (emit - recv)) / 2`), and a `{ n, p50, p90, p99, max, mean, histogram }` over the fixed `binEdgesMs` (0, 1, 2, 5, 10, 20, 50, 100, 200, 500, 1000, 2000 ms) for `emitGapMs`, `recvGapMs` and `chunkGapMs` (the per-token periods at the worker, the page and the runner), `workerMs` (the worker's time on the request), `roundTripTransitMs` (page send to page receipt minus the worker's time, both transits together, free of the clock offset), `receiptToChunkMs` and `pageTurnaroundMs` (a reply's receipt to the page's next request). All stamps are `performance.timeOrigin + performance.now()`; every statistic but `roundTripTransitMs` pairs stamps of one clock. The raw stamps are not in the run file |

Cells, the run policy, validity gates, traces and the environment capture are those of a protocol run (a profile run adds a `profile-error` trace event, `<cellId>: <reason>`, for a cell whose profile could not be taken; the cell's measurements stand), and the digest covers the field like the rest of `harness`. A control run is not a protocol run: it is never scored, never indexed, and never uploaded through the submit route (the localmode.ai runner offers Export JSON only, and the submit route answers 422 `control-run`), so it never appears in `index/summary.json` or on the leaderboard. Additive: the protocol version and the schema version are unchanged.

`controls/<kind>/<YYYY-MM-DD>/<runId>.json` holds control runs, filed by kind (`controls/order-reversed/`, `controls/fixed-order/`, `controls/wasm-default/`, `controls/wasm-q8/`, `controls/wasm-threads/`, `controls/wllama-compat/`, `controls/current-releases/`, `controls/ort-profile/`, `controls/llamacpp-profile/`) and by the UTC date of `createdAt`. A profile run's raw profile files (gzip-compressed JSON) are not filed there. They are never submitted, so the submission API never writes there: a maintainer files exported control runs into a clone with [`apps/ui/scripts/collect-control-runs.ts`](https://github.com/LocalMode-AI/LocalMode/blob/main/apps/ui/scripts/collect-control-runs.ts), which verifies each file's digest and shape (`validateSubmission`), drops a nonce if the file has one, and refuses a run id already under `runs/`, `quarantine/` or `controls/`.

## Native baselines (`native/`)

`native/YYYY/MM/<device>/` holds `llama-bench` runs made outside the browser on lab machines that also have browser runs in `runs/`, so the browser lanes can be read against the native ceiling of the same weights on the same silicon. Each directory carries `llama-bench.json` (every result object `llama-bench` emitted, concatenated in run order; `model_filename` is the bare file name), `llama-bench.md` (mean ± sd tokens/s per model and configuration), `environment.json` / `environment.txt` (machine, OS, power and thermal state, toolchain, llama.cpp build), `models.json` (file, source URL, size, SHA-256 of each GGUF, the same files the browser lanes load), and a `README.md` with every command line, the order, the waits, and anything that failed or was skipped. Shapes match the browser cells (`-p 128,512 -n 128 -pg 128,128 -pg 512,128 -r 5`; note that `tg128` generates from an empty context, so the `pg` rows are the closer analogue of the browser's decode-after-prompt). These files are maintainer-committed, carry no digest or nonce, and are not aggregated into the leaderboard.

## Protocol versions

- **`localmode-bench/5`** (2026-09-22) - the llama.cpp lanes request half the browser's logical thread count (at least two) instead of all of it, and load with a 2,048-token context (`runtimeConfig.n_ctx`; the embedding lane 512). Under v4 a pool over every logical thread ran at half speed with high variance on hybrid and SMT processors (native M1 Pro sweep: tg128 178 ± 42 tokens/s at 10 threads, 395 ± 16 at 8; in the browser the M4 Max's 16-thread pool decoded a third as fast as the M1 Pro's 10); the browser exposes no core topology, so half the logical count is the rule, and both the requested count (`n_threads`) and the pool the runtime built (`multithread`, `n_threads_used`) are recorded. The smaller context is sized to the workloads (about 700 tokens) instead of the provider's 8,192 default and shrinks the Gemma 4 E2B GGUF's KV cache on the CPU lane, under the 4 GiB link-time memory cap of wllama's memory64 build (the compatibility build for browsers without JSPI or Memory64, such as Safari, is 32-bit); it does not rescue that lane's Gemma quality cell, which still fails on the per-request state allocation (`std::bad_alloc`) with the 3.46 GB weights resident and is recorded as an error, as under v4. Every other lane measures exactly as under v4; the leaderboard shows v4 rows beside v5 rows (rows never mix versions), and nothing is re-scored. Schema and plausibility rules unchanged.
- **`localmode-bench/4`** (2026-09-20) - the llama.cpp lanes (`wllama`, `wllama-webgpu`) load every language model as text only (`runtimeConfig.mmproj: false`). Under v3 the Gemma 4 E2B pairing also loaded the 557 MB vision projector the provider catalog lists for it: unused by the text-only workloads, downloaded and CLIP-warmed inside the untimed warmup, it turned wllama's model cache off for the two-file source (the warmup and the warm reload re-downloaded the 3.46 GB weights) and did not fit the CPU lane under the 4 GiB link-time memory cap of wllama's memory64 build (all three `wllama/gemma-4-e2b` cells errored on every Thorough run). Other pairings measure exactly as under v3. wllama `warm-reload` cells carry `offloadedLayers: "unreported"` and the lane's requested backend on every run before bench 0.9.9: the warm reload times the provider's preload path (an OPFS cache probe), and llama.cpp loads in the untimed warmup of the timed cells. Since bench 0.9.9 (site build 2.16.15) the runner loads the engine untimed after the warm reload's timed span (the adapter's `settle()`, which sends the warmup probe), so the `warm-reload` cell carries the same offload report and backend as the timed cells; the timed span is unchanged. Schema and plausibility rules unchanged.
- **`localmode-bench/3`** (2026-09-20) - the wllama lane split into `wllama` (llama.cpp WASM on the CPU, `n_gpu_layers: 0`) and `wllama-webgpu` (every layer offloaded) over the same GGUF files, after llama.cpp's load log showed the v2 lane offloading to WebGPU by default on every WebGPU-capable browser while the files recorded `wasm`; cells carry `runtimeConfig`; the recorded backend follows llama.cpp's offload report. Schema and plausibility rules unchanged. Read archived v2 wllama cells as WebGPU wherever `environment.gpu.available` is true.
- **`localmode-bench/2`** (2026-09-19) - TTFT/decode derived only from genuinely incremental chunk traces (non-incremental lanes report an end-to-end rate via the `totalMs`/`overallCharsPerSec` summaries); quality lane: 48-token budget, reasoning-block stripping, uniform per-pairing no-think suffixes, raw outputs + parse rate stored; degenerate-output gate (< 16 generated chars invalidates the cell); every runtime receives the prompt as a single templated user turn with cross-request prompt caching disabled; error causes preserved; deterministic runtime execution order for reproducibility.
- **`localmode-bench/1`** (2026-09-18) - initial public protocol.
